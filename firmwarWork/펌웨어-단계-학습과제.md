# 부팅 1단계: 펌웨어 — 실습 과제 & 확인 문제

대상 장비

- **A 장비**: ThinkPad T430 — Legacy BIOS
- **B 장비**: GMKtec NucBox G3 (N100) — UEFI

두 장비가 서로 다른 부팅 모드라 비교 실습이 가능합니다. 각 과제는 A/B 양쪽에서 돌려보고 차이를 기록하는 것이 핵심입니다.

> **주의**: `dd` 명령에서 `of=/dev/sdX`는 절대 쓰지 마세요. 이 문서의 모든 `dd`는 `if=`로 읽기만 합니다. MBR을 덮어쓰면 부팅이 불가능해집니다.

## Part 1. 실습 과제

### 과제 1. 부팅 모드 판별

```bash
[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS
sudo dmidecode -t bios
efibootmgr -v
```

**기록할 것**

- 두 장비의 판별 결과
- `efibootmgr`이 A 장비에서 실패하는 이유를 한 문장으로
- BIOS 벤더, 버전, 릴리스 날짜

---

### 과제 2. 파티션 테이블 해부

```bash
sudo fdisk -l /dev/sda
sudo dd if=/dev/sda bs=512 count=1 2>/dev/null | xxd | tail -6
```

**기록할 것**

- `Disklabel type`이 `dos`인지 `gpt`인지
- 오프셋 446부터 시작하는 64바이트 영역에서, 값이 채워진 슬롯과 `00`으로 비어 있는 슬롯의 개수
- 출력 마지막 2바이트가 `55aa`인지 확인

---

### 과제 3. 리틀 엔디언 직접 계산

```bash
sudo fdisk -l /dev/sda            # Start 값을 10진수로 확인
sudo dd if=/dev/sda bs=512 count=1 2>/dev/null | xxd -s 454 -l 4
```

**과제**

1. 덤프된 4바이트를 리틀 엔디언 규칙에 따라 뒤집어 16진수 값을 구할 것
2. 그 값을 10진수로 변환할 것
3. `fdisk`의 `Start` 값과 일치하는지 확인할 것
4. 그 섹터 번호에 512를 곱해 바이트 단위 위치를 구하고, MiB로 환산할 것

오프셋 454가 나온 근거(446 + 8)를 설명할 수 있어야 합니다.

### 과제 4. 부트 갭 내용 확인 (A 장비)

```bash
sudo dd if=/dev/sda bs=512 skip=1 count=8 2>/dev/null | xxd | head -30
sudo dd if=/dev/sda bs=512 skip=1 count=8 2>/dev/null | strings | head
```

**기록할 것**

- 갭이 실제로 비어 있는지, 아니면 코드가 들어 있는지
- `strings` 출력에서 눈에 띄는 문자열
- `fdisk`의 첫 파티션 `Start` 값으로부터 갭의 크기를 계산

## Part 3. 정답 및 해설

### A. 계산 문제

**A-1.** 2^32 × 512B = 2,199,023,255,552B = 2TiB (약 2.2TB). 32비트로 표현 가능한 섹터 번호는 약 43억 개이고, 각 섹터가 512바이트이므로 곱한 값이 상한이다. 시작 LBA와 섹터 개수 **양쪽 모두** 이 제약을 받으므로, 2TiB 너머에서 시작하는 파티션도 만들 수 없다.

**A-2.** 2^32 × 4096B = 16TiB.

**A-3.** 2^64 × 512B ≈ 8ZiB. 현실적으로 도달 불가능한 크기.

**A-4.** 2047섹터 × 512B = 1,048,064B ≈ 1MiB. (LBA 0은 MBR이므로 갭은 LBA 1~2047)

**A-5.** `00 08 00 00`. 리틀 엔디언이므로 하위 바이트부터 저장된다.

**A-6.** 128개 × 128바이트 = 16KB. 디스크 끝의 백업본까지 포함하면 32KB.

---

### B. 개념 문제

**B-1.** `0x7C00`은 주소(메모리의 위치), `0x55AA`는 값(그 자리에 담긴 내용). 둘 다 `0x` 접두사를 쓰지만 성격이 다르다.

**B-2.** 펌웨어가 512바이트를 통째로 읽은 뒤 마지막 2바이트만 확인하면 되므로 검사가 단순해진다. 앞에 두면 부트 코드 공간이 2바이트 줄고, 위치도 고정하기 어려워진다.

**B-3.** 리얼 모드에서 CPU가 인터럽트 발생 시 `0x0000`부터 시작하는 표를 참조하도록 하드웨어적으로 정해져 있다. 옮길 수 없다.

**B-4.** 스택은 push할 때마다 주소가 감소한다. `0x7C00`에 스택 포인터를 두면 스택은 `0x7BFF` 아래로 자라고, MBR 코드는 `0x7C00`부터 위로 512바이트를 차지하므로 서로 충돌하지 않는다.

**B-5.** 파티션 테이블은 고정 크기 배열이다. 시그니처가 항상 오프셋 510에 있어야 하고 부트 코드가 "446번지의 4개짜리 배열"을 전제로 하드코딩되어 있으므로, 슬롯 개수는 가변이 될 수 없다. 빈 슬롯은 `00`으로 채워진다.

**B-6.** CHS 시작 3바이트 + CHS 끝 3바이트. 옛 CHS 주소 지정 방식 호환을 위해 남겨두었으나 8GB 이상 디스크를 표현할 수 없어 현재는 더미 값이 들어간다.

**B-7.** IVT의 해당 항목(디스크는 19번, 오프셋 `0x4C`)에 적힌 주소를 자기 코드 주소로 덮어쓴다. 이후 누가 `INT 13h`를 호출하면 원래 BIOS 코드 대신 옵션 ROM의 코드가 실행된다.

**B-8.** 열거 시점에는 아직 `INT 13h` 핸들러가 IVT에 등록되지 않았다. 핸들러를 채우는 주체가 펌웨어 자신이고, 그것은 열거를 마쳐야 가능하다. 대신 I/O 포트 `0xCF8`(주소)과 `0xCFC`(데이터)에 `in`/`out` 명령으로 직접 접근해 PCIe 설정 공간을 읽는다.

**B-9.** 리눅스 커널이 프로텍티드 모드로 전환하는 시점. 리얼 모드 인터럽트 체계가 더는 동작하지 않으며, 이후 커널은 자체 드라이버로 디스크에 접근한다.

**B-10.** 부트 서비스는 메모리 할당·파일 읽기 등 부트로더가 쓰는 기능이며 커널이 `ExitBootServices()`를 호출하면 사라진다. 런타임 서비스는 NVRAM 변수 접근·재부팅 등으로 OS 동작 중에도 유지된다. `efibootmgr`은 런타임 서비스 덕분에 동작한다.

**B-11.** 구현이 단순해 펌웨어에 넣기 쉽고 특허 문제가 정리되었다. 성능이 중요한 영역이 아니라 단순함이 우선이다.

**B-12.** 리얼 모드 주소 공간에서 옵션 ROM에 배정된 구간이 `0xC0000`~`0xDFFFF`로 고정되어 있기 때문이다.

**B-13.** `grub-install`이 실제 `/boot` 환경을 조사해 필요한 모듈만 골라 조립한다. LVM 위라면 `lvm.mod`가 들어가고 아니면 빠지므로 크기가 달라진다.

**B-14.** `core.img`의 역할은 파일시스템을 읽을 수 있는 상태까지 도달하는 것까지다. 거기 도달하면 `grub.cfg`는 `/boot/grub`에서 일반 파일로 읽을 수 있으므로 포함할 이유가 없다. 갭 공간도 한정적이다.

**B-15.** DDR4-3200은 1비트에 약 312ps만 주어진다. 배선 길이·온도·전압·칩 개체 편차 때문에 신호 도착 시각이 핀마다 어긋나므로, 실제로 패턴을 쓰고 읽으며 딜레이를 쓸어 "제대로 읽히는 구간"의 중앙을 찾아야 한다.

### C. 시나리오

**C-1.** MBR의 32비트 LBA 필드 한계. GPT로 전환해야 한다(디스크 재파티셔닝 필요).

**C-2.** 옵션 ROM 공간(`0xC0000`~`0xDFFFF`, 128KB) 부족. 카드가 늘어나면서 일부 ROM이 적재되지 못한다. 안 쓰는 장치의 옵션 ROM을 펌웨어에서 비활성화하거나 UEFI 모드로 전환한다.

**C-3.** 부팅 모드 불일치. A는 BIOS 모드로 설치되어 MBR+부트 갭 구조이고, B는 UEFI라 ESP의 `.efi` 파일을 찾는다. 서로 호환되지 않는다.

**C-4.** MBR과 부트 갭. 이 영역은 어떤 파티션에도 속하지 않으므로 파티션 단위 백업에서 누락된다. `core.img`가 사라져 부팅 불가.

**C-5.** RAID 카드의 옵션 ROM 코드가 출력한다. 부팅 4단계(옵션 ROM / UEFI 드라이버 실행)에 해당한다.

**C-6.** 시큐어 부트가 활성화되어 서명되지 않은 모듈을 거부하고 있다. MOK에 자신의 키를 등록하고 모듈에 서명하거나, 시큐어 부트를 비활성화해야 한다.

**C-7.** 메모리 구성이 바뀌어 저장된 트레이닝 결과(MRC 캐시)가 무효화되었고, 펌웨어가 DRAM 트레이닝을 처음부터 다시 수행했다. 성공한 값이 다시 저장되어 두 번째 부팅부터는 재사용된다.

**C-8.** 펌웨어 설정에서 VT-d(IOMMU)가 활성화되어 있는지 확인한다. 그다음 커널 커맨드라인에 `intel_iommu=on`이 있는지, `dmesg | grep -i DMAR`로 실제 활성화되었는지 확인한다.

**C-9.** 카드의 Expansion ROM에 코드 타입 0(x86 리얼 모드)만 들어 있고 타입 3(EFI 이미지)이 없는 경우다. UEFI 펌웨어는 타입 3만 실행하므로 인식되지 않는다. CSM이 있으면 우회 가능하나 최신 보드에는 없다.

**C-10.** 부트 순서와 펌웨어 설정이 초기화된다. VT-x/VT-d가 꺼져 VM이 기동하지 않거나, 부팅 장치를 찾지 못하는 증상이 나타날 수 있다. 시각도 초기화되어 인증서 검증 등에 영향을 줄 수 있다.

### D. 서술형 채점 포인트

**D-1.** 다음이 포함되면 충분하다.
- 부트로더 위치: MBR 512B + 부트 갭 vs ESP의 `.efi` 파일
- 파티션 방식: MBR(4개, 2TiB) vs GPT(128개, 사실상 무제한, 백업 헤더)
- 실행 모드: 16비트 리얼 모드 vs 64비트
- 확장 카드: 옵션 ROM 인터럽트 훅(128KB 제약) vs UEFI 드라이버 프로토콜 등록
- 부팅 설정: 디스크 순서만 vs NVRAM 엔트리(파일 경로까지), OS에서 변경 가능
- 보안: 없음 vs 시큐어 부트(PK/KEK/db/dbx, shim, MOK)

**D-2.** 추상화는 하나의 실제 장치를 공통 인터페이스로 감싸는 것이고(`INT 13h`, Block I/O 프로토콜), 가상화는 하나를 여럿으로 나누거나 없는 것을 만들어내는 것이다. 펌웨어는 BAR 할당과 IRQ 라우팅으로 실제 장치에 실제 자원을 배분할 뿐이다. 가상화는 KVM/QEMU 계층의 일이며, 펌웨어는 VT-x/VT-d를 활성화해 주는 위치에 있다.

**D-3.** 대응 관계
- 446B 부트 코드 부족 → 부트 갭에 `core.img` 배치 / UEFI는 크기 제약 없는 `.efi` 파일
- 파일시스템 밖에 코드를 둠 → 백업·덮어쓰기 문제 / UEFI는 ESP라는 정식 파티션이 보호
- 파티션 4개, 2TiB 한계 → 확장 파티션 우회 / GPT가 근본 해결
- 옵션 ROM 128KB → 카드 개수 제한 / UEFI 드라이버는 제약 없음
- OS에서 부팅 설정 변경 불가 → 없음 / 런타임 서비스로 `efibootmgr` 지원

**D-4.** 부트 갭은 파일시스템 밖이라 어떤 보호도 받지 못하며, 파티션 단위 백업에서 누락되고 다른 OS 설치에 덮어쓰일 수 있다. 복구하려면 `grub-install`을 다시 실행해야 한다. ESP는 FAT32 파티션 안의 파일이므로 `cp`로 백업·복원되고, 벤더별 디렉터리로 분리되어 충돌하지 않는다. 단 NVRAM 엔트리는 메인보드에 있어 디스크와 함께 이동하지 않으므로, 장비 교체 시 `efibootmgr` 재등록이나 폴백 경로가 필요하다.

- [ ] UEFI 부팅 체인을 NVRAM 엔트리부터 순서대로 말할 수 있다
- [ ] C 파트 시나리오 10개 중 8개 이상을 즉답할 수 있다
